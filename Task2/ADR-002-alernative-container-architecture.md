# ADR-002: Выбор архитектурного стиля для Edge-Cloud взаимодействия

## ADR-002-alternative: Выбор подхода к взаимодействию Edge-Cloud

### Контекст

Система мониторинга свиноводческих ферм требует организации взаимодействия между Edge-агентами (на фермах) и облачной платформой (в головном офисе). Ключевые требования:

- Работа в условиях нестабильного интернета
- Задержка оповещения < 5 секунд
- Отказоустойчивость 99,95%
- Синхронизация данных с задержкой до 10 минут
- Минимизация потери данных при обрыве связи

Необходимо выбрать архитектурный подход для передачи данных между Edge и Cloud.

---

## Вариант 1: Событийно-ориентированный подход с накоплением данных

### Решение

Использовать событийно-ориентированную архитектуру с локальным брокером сообщений на Edge и асинхронной репликацией в облако.

### Архитектурная диаграмма

*Диаграмма представлена в файле c2-alternative-event-driven-containers-architecture.puml*

### Поток данных

**Нормальный режим (есть интернет):**

1. Edge генерирует события → локальный брокер
2. Sync Agent читает и передает в облако
3. Cloud Broker распределяет по сервисам
4. Сервисы обрабатывают и сохраняют

**Офлайн режим (нет интернета):**

1. Edge генерирует события → локальный брокер
2. События сохраняются в локальном хранилище
3. Локальные оповещения работают (worker получает < 5 сек)
4. При восстановлении связи Sync Agent передает все накопленные данные

### Преимущества

1. Полная автономность - работа без интернета
2. Нулевая потеря данных - все сохраняется локально
3. Оптимизация трафика - передача только изменений
4. Асинхронная синхронизация - не блокирует основные процессы
5. Высокая отказоустойчивость - распределенное хранение
6. Возможность приоритезации - критичные данные передаются первыми

### Недостатки

1. Сложность архитектуры - много компонентов
2. Требуется локальное хранилище - дополнительные затраты
3. Риск конфликтов данных - при параллельных изменениях
4. Сложность отладки - распределенная система
5. Задержка синхронизации - до 10 минут

### Компромиссы

| Аспект | Плюсы | Минусы |
|--------|-------|--------|
| Сложность | Гибкость распределенной системы | Сложнее разработка и поддержка |
| Стоимость | Оптимизация трафика | Дороже из-за Edge-оборудования |
| Надежность | Отказоустойчивость | Сложность обеспечения консистентности |
| Производительность | Минимальная задержка | Накладные расходы на очереди |

### Технологический стек

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| Edge Broker | EMQX | Специализированный MQTT для IoT, персистентность |
| Cloud Broker | RabbitMQ | Поддержка MQTT, кластеризация, AMQP |
| Локальное хранилище | TimescaleDB | Временные ряды, сжатие, репликация |
| Синхронизация | Rust + Protobuf | Производительность, компактность |
| Протокол | MQTT + AMQP | Легкий, надежный, поддержка офлайн |

### Ограничения

1. При нагрузке > 100K сообщений/сек потребуется Kafka
2. Требуется механизм разрешения конфликтов
3. Необходим мониторинг очередей
4. Ограниченный объем локального хранилища

## Вариант 2: Синхронный REST подход с прямой передачей

### Решение

Использовать синхронную REST архитектуру с прямой передачей данных из Edge в Cloud при наличии интернета.

### Архитектурная диаграмма

*Диаграмма представлена в файле c2-alternative-rest-containers-architecture.puml*

### Поток данных

**Нормальный режим (есть интернет):**

1. Edge генерирует событие
2. Edge Gateway вызывает REST API облака
3. API Gateway маршрутизирует запрос
4. Сервис обрабатывает и сохраняет

**Офлайн режим (нет интернета):**

1. Edge генерирует событие
2. Edge Gateway пытается отправить в облако
3. При ошибке - сохраняет в Redis с TTL
4. Sync Agent периодически retry отправку
5. Если данные устарели - удаляются

### Преимущества

1. Простота архитектуры - минимальное количество компонентов
2. Быстрая разработка - стандартный REST подход
3. Меньше затрат - не требуется сложное Edge-оборудование
4. Легкая отладка - синхронные вызовы
5. Стандартные технологии - легко найти специалистов
6. Мгновенная синхронизация - данные сразу в облаке

### Недостатки

1. Зависимость от интернета - без связи система не работает
2. Потеря данных - при обрыве связи во время отправки
3. Высокий трафик - постоянные синхронные запросы
4. Задержки при передаче - блокирующие вызовы
5. Нагрузка на API - большое количество запросов
6. Ограниченная автономность - только кэширование на время

### Компромиссы

| Аспект | Плюсы | Минусы |
|--------|-------|--------|
| Сложность | Простая архитектура | Нет гибкости распределенной системы |
| Стоимость | Дешевле MVP | Дороже трафик и облачные ресурсы |
| Надежность | Простота поддержки | Зависимость от интернета |
| Производительность | Мгновенная синхронизация | Блокирующие вызовы |

### Технологический стек

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| Edge Gateway | FastAPI | Простой REST, быстрое создание API |
| API Gateway | Kong | Маршрутизация, аутентификация |
| Кэш | Redis | Быстрое временное хранение |
| Синхронизация | Python + Requests | Простые HTTP вызовы |
| Протокол | HTTPS/JSON | Стандартный, легко отлаживать |

### Ограничения

1. Не подходит для нестабильного интернета
2. Потеря данных при обрыве связи
3. Ограниченный объем кэша (Redis)
4. Нет механизма гарантированной доставки
5. Проблемы с масштабированием (нагрузка на API)

## Рекомендация

### Выбрано: Вариант 1 - Событийно-ориентированный подход с накоплением

**Обоснование:**

1. Полное соответствие нефункциональным требованиям:
    - Работа офлайн (требование №1) - критично для ферм
    - Отказоустойчивость 99,95% (требование №4)
    - Синхронизация до 10 минут (требование №7)

2. Реальные условия эксплуатации:
    - Нестабильный WiFi на фермах
    - Критичность потери данных
    - Автономность критических функций

3. Долгосрочная стратегия:
    - Масштабируемость на тысячи ферм
    - SaaS потенциал
    - Конкурентное преимущество

4. Бизнес-ценность:
    - Минимальные потери данных
    - Высокая надежность
    - Оптимизация трафика

**Компромиссы, которые мы принимаем:**

- Более сложная разработка (но это оправдано требованиями)
- Более высокая стоимость Edge-оборудования (но окупается надежностью)
- Сложнее поддержка (но система будет надежнее)

---

## Решение

**Утвердить событийно-ориентированный подход с накоплением данных (Вариант 1) как основную архитектуру для Edge-Cloud взаимодействия.**

**План внедрения:**

1. Фаза 1 (MVP): Базовая реализация с EMQX и RabbitMQ
2. Фаза 2: Добавление TimescaleDB для локального хранения
3. Фаза 3: Внедрение механизма разрешения конфликтов
4. Фаза 4: Переход на Kafka при необходимости

---

## Альтернативный вариант (отклонен)

**REST подход с прямой передачей (Вариант 2)** отклонен по следующим причинам:

1. Не удовлетворяет требованию работы офлайн
2. Возможна потеря критических данных
3. Высокая нагрузка на каналы связи
4. Не обеспечивает 99,95% отказоустойчивости
5. Не масштабируется на большое количество ферм
