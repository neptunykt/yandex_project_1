## Контекст и проблема

Бизнесу необходимо утвердить архитектуру MVP агро-ИТ системы для мониторинга свиноводческих ферм. Ключевые требования:

- Задержка оповещения менее 5 секунд (NFR-02)
- Работа в условиях нестабильного интернета (NFR-01)
- Отказоустойчивость 99,95% (NFR-04)
- Синхронизация с облаком с задержкой до 10 минут (NFR-07)
- Работа офлайн с последующей синхронизацией (NFR-08)

**Критическое ограничение для MVP:** Централизованное решение без Edge-контура не выполняет обязательные условия автономной работы и реакции за 5 секунд при нестабильной связи. Edge-контур является обязательным компонентом уже на этапе MVP.

## Вариант 1: Централизованное решение (ОТКЛОНЕН)

### Концепция

Все компоненты системы (видеоаналитика, управление, хранение) работают в облаке. На ферме только минимальный набор оборудования для передачи данных.

### Как работает

1. Камеры передают RTSP поток напрямую в облако через интернет
2. Видеоаналитика с нейросетью запускается в облаке (GPU-инстансы)
3. Команды на кормушки и поилки отправляются из облака через интернет (MQTT over WebSocket)
4. При обрыве интернета базовая работа оборудования сохраняется (локальный контроллер), но видеоаналитика и оповещения недоступны
5. Все данные хранятся централизованно в облаке

### Преимущества

1. Низкая стоимость — не требуется мощное Edge-оборудование (NVIDIA Jetson) на каждой ферме
2. Быстрое внедрение — разработка и деплой только одного центрального компонента
3. Простота поддержки — обновление системы в одном месте, без управления распределенными агентами
4. Быстрый вывод на рынок — можно запустить на 2-3 фермах за 2-3 месяца

### Недостатки (КРИТИЧЕСКИЕ)

| № | Недостаток | Влияние на бизнес |
|---|------------|-------------------|
| 1 | Зависимость от интернета | При обрыве связи система не работает, животные остаются без мониторинга |
| 2 | Задержка более 5 секунд | Зависит от скорости интернета, нарушает NFR-02 |
| 3 | Нет работы офлайн | Нарушает NFR-08 |
| 4 | Единая точка отказа | Падение облака останавливает все фермы |
| 5 | Высокие затраты на трафик | RTSP видео идет в облако (дорого) |

### Технологический стек

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Бэкенд | Python (FastAPI) + PostgreSQL | Быстрая разработка, единая кодовая база |
| Видеоаналитика | Python + GPU (Yandex Cloud/AWS) | Готовая нейросеть от партнеров, мощные GPU в облаке |
| Брокер | RabbitMQ или Redis Pub/Sub | Легковесный, простой в настройке |
| Фронтенд | React (Web) + Flutter (Mobile) | Кроссплатформенность, быстрая разработка |
| Хранилище | PostgreSQL + MinIO (S3) | Все данные в одном месте |
| Аутентификация | Keycloak (базовая) | OAuth2/OIDC для безопасности |

### Почему отклонен для MVP

Решение НЕ соответствует критическим требованиям:

1. NFR-01 (Надежность): Не работает при нестабильном интернете
2. NFR-02 (Производительность): Задержка более 5 секунд
3. NFR-08 (Работа офлайн): Полная остановка при обрыве связи

**Вывод:** Централизованное решение не может быть рекомендовано для MVP, так как не обеспечивает выполнение обязательных требований бизнеса.

## Вариант 2: Гибридная Edge-Cloud архитектура (РЕКОМЕНДУЕТСЯ)

### Концепция

Критичные для быстрого реагирования компоненты (видеоаналитика, управление кормлением, локальные оповещения) размещаются на фермах (Edge), обеспечивая работу офлайн и задержку менее 5 секунд. Центр используется для агрегации, аналитики и управления пользователями.

### Как работает

**Нормальный режим (есть интернет):**

1. Камеры передают видео на Edge-агент (локальная видеоаналитика, менее 5 сек)
2. Edge-агент отправляет локальное оповещение (мгновенно)
3. Edge-агент асинхронно передает события и метрики в облако
4. Облако обеспечивает аналитику, отчеты, интеграцию с ERP

**Офлайн режим (нет интернета):**

1. Камеры передают видео на Edge-агент (локальная видеоаналитика работает)
2. Edge-агент отправляет локальное оповещение (worker получает менее 5 сек)
3. Данные накапливаются в локальном хранилище (TimescaleDB)
4. При восстановлении связи происходит синхронизация с облаком

### Ключевые компоненты

| Компонент | Edge (ферма) | Cloud (центр) |
|-----------|--------------|---------------|
| Видеоаналитика | NVIDIA Jetson + TensorRT | Только агрегация |
| Управление кормлением | Локальный контроллер (Modbus) | Управление расписанием |
| Хранилище | TimescaleDB (2 недели) | ClickHouse (5+ лет) |
| Оповещения | Локальные (WebSocket) | Глобальные (Push, Email, SMS) |
| Синхронизация | Sync Agent (Rust) | RabbitMQ или Kafka |
| Брокер | EMQX (MQTT) | RabbitMQ |

### Преимущества

1. Полная автономность — работа без интернета (NFR-01)
2. Задержка менее 5 секунд — видеоаналитика на месте (NFR-02)
3. Распределенная отказоустойчивость — отказ одной фермы не влияет на другие (NFR-04)
4. Экономия трафика — в облако идут только события, а не видео
5. Масштабируемость — неограниченное количество ферм (NFR-05)
6. Синхронизация — до 10 минут задержки (NFR-07)

### Недостатки

1. Высокая стоимость — Edge-оборудование (от 2000 долларов на ферму)
2. Долгое внедрение — разработка распределенной системы (4-6 месяцев)
3. Сложная поддержка — нужно управлять обновлениями на всех фермах
4. Сложность отладки — распределенная система сложнее в диагностике

### Технологический стек

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Edge Video Analytics | Python + TensorRT + NVIDIA Jetson | Оптимизация для GPU, низкая задержка |
| Edge Management | Rust + Python | Производительность, безопасность |
| Edge Broker | EMQX | Специализированный MQTT для IoT |
| Edge Storage | TimescaleDB + Redis | Временные ряды, кэширование |
| Sync Agent | Rust + Protobuf | Компактность, производительность |
| Cloud Broker | RabbitMQ | Поддержка MQTT, кластеризация |
| Cloud Storage | ClickHouse + PostgreSQL + MinIO | Аналитика, оперативные данные, видео |
| API Gateway | Kong | Маршрутизация, аутентификация |
| Auth | Keycloak | OAuth2/OIDC |

## Рекомендация

### Выбрано: Вариант 2 - Гибридная Edge-Cloud архитектура

**Обоснование:**

1. Полное соответствие критическим NFR:
    - NFR-01 (Надежность): работа офлайн
    - NFR-02 (Производительность): задержка менее 5 секунд
    - NFR-04 (Отказоустойчивость): 99,95%
    - NFR-08 (Работа офлайн): полная автономность

2. Реальные условия эксплуатации:
    - Нестабильный WiFi на фермах
    - Критичность потери данных
    - Автономность критических функций

3. Долгосрочная стратегия:
    - Масштабируемость на тысячи ферм
    - SaaS потенциал
    - Конкурентное преимущество

4. Бизнес-ценность:
    - Минимальные потери данных
    - Высокая надежность
    - Оптимизация трафика

**Компромиссы, которые мы принимаем:**

- Более высокая стоимость MVP (но это оправдано требованиями)
- Более сложная разработка (но система будет надежнее)
- Сложнее поддержка (но это обеспечивает автономность)
